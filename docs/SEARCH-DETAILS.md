# 動画情報・投稿期間・キャッシュ対策

## 使い方

検索対象、並び順、投稿期間、検索語を指定して「検索」を押します。
期間の選択だけでは実行されません。「もっと見る」は直前に実行した条件の続きを取得します。
「固定の一覧に戻す」で条件を初期値へ戻します。固定一覧は検索条件の対象外です。

## カードに情報を足す仕組み

「追加情報」はタイトル以外の公開日時・再生数・投稿者などです。
`app/models.py`のVideoが各サイト共通の受け渡し形式を定義します。
`app/search.py`が検索結果を共通形式に変換し、`app/metadata.py`が不足する情報を補います。

- YouTube：search.listのsnippetから公開日時・投稿者を取得し、表示対象の最大6IDをvideos.listへ1回まとめて送り、再生数を取得します。
- ニコニコ：スナップショット検索のstartTime、viewCounter、userId/channelIdを取得します。表示名はgetthumbinfoのuser_nickname/ch_nameで補います。
- getthumbinfoは検索APIとは別の補助エンドポイントです。取得できなければ投稿者IDを残し、動画の表示は継続します。将来の提供継続は保証しません。
- 追加情報は最大4秒で切り上げます。ニコニコの補助取得は同時2接続まで、個別のHTTPタイムアウトは1秒です。
- 詳細の応答順には頼らず動画IDで結び付けます。削除などで情報がない場合はnullを使い、架空の数値や名前を補いません。

初回と「もっと見る」の各ページでは、YouTubeは検索1回＋詳細1回、ニコニコは検索1回＋名前取得最大6回です。
同じページの成功結果は追加情報も含めて60秒保存し、無駄な通信を抑えます。先読みはしません。
追加情報取得に失敗したページも検索結果は保存します。不足情報の再取得は60秒経過後の再検索で行えます。
キーはGoogle宛てのヘッダーのみで送り、ニコニコや画面へは送りません。

固定12本の追加情報は2026-11-24に取得し、videos.jsonに保存した値です。
固定一覧の読み込みでは外部APIを呼びません。再生数は取得日時の値であり、現在値ではありません。
日付は日本時間で表示します。検索インデックスと追加情報の更新差により、並び順と表示再生数が厳密には一致しないことがあります。

## 期間を揃える仕組み

`app/filters.py`が「最近7日・30日・365日」をUTCの開始日時と終了日時へ変換します。
秒以下を切り捨て、同じ分に実行した同条件の検索でキャッシュを共有します。
YouTubeにはpublishedAfter/publishedBefore、ニコニコにはfilters[startTime][gte]/[lte]を送ります。
両サイトとも境界時刻を含む範囲です。期間指定なしでは日時フィルターを送りません。

【根幹】ページを進めるときに現在時刻から計算し直すと、対象範囲がずれて動画を飛ばす原因になります。
そのため、`app/pagination.py`の署名付きカーソルに最初の日時範囲も含め、続きと再試行で同じ値を使用します。
別の期間に変更したカーソルは410で拒否します。日次スナップショット自体の更新や動画削除による結果変動までは防げません。

## 古いCSS・JavaScriptを使わせない仕組み

ブラウザの「キャッシュ」は、通信を減らすためファイルを保存して再利用する仕組みです。
従来はHTMLだけが更新され、保存された古いCSS/JavaScriptが残ることがありました。

`app/main.py`はHTMLを返す際、CSSとJavaScriptの内容からSHA-256という識別値を計算します。
この識別値を`?v=...`として読み込みURLに付けるため、内容が変わると別のURLになります。
更新日時やファイルサイズだけには頼りません。HTML/CSS/JavaScriptにはCache-Control: no-storeも設定します。

更新後は新しいコードでサーバーを再起動し、画面を再読み込みします。
旧版が保存したファイルから初めて切り替えるときはCtrl+F5が必要な場合があります。
開いたままの画面を自動で書き換える仕組みではありません。
