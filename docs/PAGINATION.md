# 「もっと見る」の仕組み

## 利用者から見た動き

最初の検索で各サイト最大6本を表示します。下部の「もっと見る」を押すと、各サイトの次のページを取得して末尾に追加します。
次ページの先読みはしません。表示済みの動画は残り、同じ動画IDは重複して追加しません。
結果が尽きたサイトには通信せず、残っているサイトだけ続けます。
追加中に別の検索をした場合は、古い結果が新しい一覧へ混ざらないようにしています。

一部のサイトが失敗した場合は、次の二つの操作ができます。

- 「取得できなかったサイトを再試行」：失敗したサイトの同じページだけを取得する。
- 「もっと見る」：成功サイトの続きを取得し、失敗サイトも同じ位置から再試行する。

通信自体が失敗したときも、一覧を消さず追加読み込みを再試行できます。
APIの応答順序やランキングが変わると同じ動画が返る場合があります。重複は画面で除くため、追加件数が12本未満になることがあります。

## バックエンドが管理する「しおり」

カーソルは、どこまで読み進んだかを伝える文字列です。
検索対象もカーソルに紐づきます。続きの取得には最初と同じ検索対象を指定し、別対象へ変更する場合は先頭から検索し直します。
YouTubeのnextPageTokenと、ニコニコの_offsetをまとめて画面に返します。
画面はこれを保存し、次のボタンクリックでAPIに渡します。
この文字列に署名を付け、位置や検索語を書き換えた要求を検出します。暗号化ではなく改ざん検出であり、秘密のAPIキーは含みません。

YouTubeはページの取得件数を6件に揃え、取得した候補を途中で捨てて次ページへ進めることを避けています。
ライブ等を除いた結果が0本でも、nextPageTokenがあれば次のページを要求できます。
ニコニコは表示できた動画数ではなく、元のdata件数だけ_offsetを進めます。

## コードを読む順番

1. `frontend/app.js` のloadVideos：初回は置き換え、append=trueなら追加する。
2. `backend/app/main.py` のsearch_videos：検索語とcursorを受け取る。
3. `backend/app/search.py` のsearch：サイト別に成功・失敗を集め、次のカーソルを作る。
4. 同ファイルの_next_position：APIの応答から次ページ位置を決める。
5. `backend/app/pagination.py`：署名・検索語・期限を検証する。

## 制約

- カーソルは発行から30分有効。サーバー再起動時も無効になり、画面の再検索ボタンでやり直します。
- 現在の署名鍵・キャッシュ・アクセス間隔はプロセス単位です。ローカルの単一サーバー用で、複数ワーカーへ展開する前に共有管理が必要です。
- ニコニコは_offsetの上限100000までで止め、画面に理由を表示します。
- 検索結果は固定スナップショットとして保存していません。検索中の投稿・削除・順位変更による取得漏れまで保証するものではありません。
- 追加取得もAPIの利用枠を使用します。連打による二重通信を防ぎ、同じページの成功応答は60秒キャッシュします。
